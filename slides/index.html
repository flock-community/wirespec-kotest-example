From contract
to tested service

One Wirespec file. A Spring Boot service and Kotest integration tests, both generated from that contract. In 10 commits.

github.com/flock-community/wirespec-kotest-example

Welcome. This talk follows a repository that goes from one Wirespec contract to a Spring Boot service with Kotest integration tests, one commit per step. Every step is tagged, so you can check out any step afterwards and run it.

The story

A small library service

Books

Put books on the shelf and list them by genre.

REST

Loans

Borrow and return. A 409 when that is not allowed.

Business rules

Ratings

Averaged from the reviews on an external review platform.

Downstream HTTP

Donations

Donated books arrive on a Kafka topic.

Async messaging

Every part of it is described in a Wirespec contract, and tested from that same contract.

The example is deliberately small but touches everything a real service has: a REST API, a business rule that can fail, a call to another team's service, and asynchronous messaging.

The problem

Integration tests drift away from the API

Hand-written JSON

Rename a field in the API and the test still compiles. It just sends the wrong body.

The same test data everywhere

Every test adds Dune by Frank Herbert. Edge cases never show up.

Untyped assertions

JsonPath strings and raw status codes instead of the types the API defines.

Nobody checks the contract

An undeclared 500 or a body of the wrong shape slips through if no assertion looks at it.

Most of us have written integration tests like this. They work, but they are not connected to the API they test. We will see such a test in step 5.

The idea

What if the tests came from the contract too?

Production code and test code from one source of truth.

Wirespec compiles the contract to Kotlin. IR extensions add to what is generated: one puts the Spring annotations on the handlers, the other generates a typed test DSL built on Kotest generators. That last one is what this talk is about.

01

Write the contract

One file describes the whole API. No code yet.

git checkout step-01

Step 01

library.ws

The complete contract of step 1, without its doc comments. BookId and Isbn are refined types: Strings constrained by a regex. Genre is an enum. BookInput is what a librarian sends, Book is what the API returns, and ApiError is the body of every failure. The five endpoints use a query parameter, path parameters and a request body, and list every status they can answer. Remember the regexes and the declared statuses; both come back later. The test generators produce values that match the regexes, and every response a test receives is checked against these statuses.

06

Generate the Kotest DSL

One more IR extension, and the contract becomes a test DSL.

git checkout step-06

Step 06

KotestDslExtension generates a typed DSL

build.gradle.kts

A Sync task moves the generated kotest package to the test source set, so Kotest stays out of the production jar.

GeneratedGives you
BookInput.generate { }an Arb<BookInput>: valid books, pinning what you set
AddBook.generate.request { }an Arb of requests with path, query, body blocks
AddBook.generate.response201 { }an Arb per declared response
.call()sends a generated request, returns the typed response
.mock { }stubs a downstream service with a generated response
.send()publishes a generated message to a channel
One file per type and per endpoint lands in the kotest package. Everything returns a Kotest Arb, which is what makes the rest possible. To hang BookInput.generate on the type, the extension adds an empty companion object to each record; the models stay free of Kotest.

Step 06

generate is an extension, not part of your model

generated in the kotest package (abridged)
in a test
  • Not a member: endpoint objects and models stay plain Kotlin.
  • Models only get an empty companion object, the receiver for BookInput.generate.
  • Compiled with the tests only. One import brings them all in.
generate is not a member of AddBook or BookInput. For endpoints, and later for channels, it is an extension property that returns a small builder object with request, response201 and so on. For records it is an extension function on the companion object, which is why KotestDslExtension adds an empty companion object to every model. Because they are extensions in the kotest package, they only exist in the test source set: production code never sees them. Kotlin imports by name, so the single import of contract.kotest.generate brings every generate into scope.

Step 06

Generated data, no Spring needed

GeneratedDataTest.kt
BookInput.generate().draw()
field slots

Reverse regex. Refined types are generated by running their regex backwards (with rgxgen): /^97[89][0-9]{10}$/g → 9797433818565, 9799713690494, 9784216295930. Every value passes validate(), so checkAll above never fails on the contract.

ISBNs are generated with a reverse regex: rgxgen runs the regex from library.ws backwards and produces strings that match it, so every generated ISBN is valid by construction. Enums are drawn from their entries, and strings get readable values that start with the field name. The lower-level API, kotestWirespecKotlinGenerator(seed), drives the generators from step 2 and is deterministic per seed.

Step 07

Tell the DSL how to reach the app

LibraryApi.kt
BookApiTest.kt

Serialization: the application's own Wirespec.Serialization bean, so tests write and read JSON exactly like the service.

Transportation: HttpTransportation from the Wirespec JVM integration, on the JDK HttpClient, to the random port.

WirespecEndpointExtension is a Kotest extension. It puts the serialization and the transport in the coroutine context of each test, and call() picks them up. The spec registers it with extension(libraryApi).

Step 09

.mock { } is the counterpart of .call()

call(): generate a request and send it.

mock { }: generate a response and stub it, for every request the typed predicate accepts.

MockServer has two methods. A WireMock version takes about 30 lines.

The predicate receives a typed GetReviews.Request, so it reads request.queries.isbn. The stub is serialized with the application's own serialization, so it sends exactly the JSON the generated client expects.

Step 09

The downstream contract is a generator for realistic answers. The unmatched stub returns a 404 that GetReviews does not declare, the generated client throws, the app answers 500, and the GetRating contract check fails the test.

Step 10

.send() a message, then eventually check the shelf

send() returns the message it generated and published.

ChannelTransport has one method. A KafkaProducer version takes about 20 lines.

No Docker: the Kafka broker and WireMock run inside the test JVM.

The channel DSL covers the sending side. Combined with the endpoint DSL and Kotest's eventually, one test drives Kafka in and checks the result over HTTP.

Recap

One contract, four entry points

You writeIt doesBacked by
BookInput.generate { title("Dune") }an Arb of contract-valid valuesplain Kotest
AddBook.generate.request { }.call()sends a request, returns the typed responseWirespecEndpointExtension
GetReviews.generate.response200 { }.mock { }stubs a downstream serviceWirespecMockExtension
BookDonations.generate.message { }.send()publishes a message to a channelWirespecChannelExtension

Every entry point is a Kotest Arb: checkAll, Exhaustive, shrinking and eventually all work.

Four entry points, three small extensions. Transportation, MockServer and ChannelTransport are tiny interfaces, so you can bring your own HTTP client, mock server or broker.

Takeaways

What you get

One source of truth

Production code, clients and the test DSL are generated from the same contract.

Pin what matters

A scenario spells out what it is about. Everything else is generated, and valid.

The contract checks every call

Undeclared statuses and bodies of the wrong shape fail the test.

All of Kotest

Property tests, shrinking and eventually, against the real service.

Wrap up: the contract is no longer only documentation. It drives the code and the tests, and the tests check the code against it on every call.
